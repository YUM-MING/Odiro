## 운영 규칙

- **daily-ingest(매일 06:30 KST)·main 푸시 배포가 끝난 뒤 측정하고, 측정 전후 GitHub Actions 에서 배포가 없었는지 사용자가 확인한다.** 측정 도중 배포가 있었으면 그 묶음은 같은 조건의 측정으로 보지 않고 다시 잰다.
- 측정 스크립트는 실제 코스를 만든다 → OpenAI·Tavily·카카오 등 외부 API 비용이 든다. 사용자가 직접 실행한다.
- 같은 요청을 반복하면 서버의 결과 캐시(같은 요청 7일)·도구 캐시(카카오 24시간, 경로·웹 검색 7일, 날씨 3시간)가 쓰인다. **캐시를 지우거나 `refresh` 로 강제로 건너뛰지 않는다.** 대신 실행 계획을 서로 다른 요청으로 만든다 (아래 "실행 계획").
- 네 측정(유휴 후 첫 요청·연속 20·동시 3·동시 5)은 **같은 날, 같은 `--avoid` 로** 돌린다. 날짜가 실행한 날 기준이라 날을 넘기면 조합이 바뀌고, `--avoid` 가 다르면 슬롯 배정이 달라진다. `--check-against cache/stability/*.json` 이 이전 측정과 겹치는 조합을 실행 전에 막는다.
- 그래도 측정 밖의 요청(사이트 확인 등)과 겹치면 결과 캐시가 쓰일 수 있다. 응답의 `meta.cached` 로 캐시 회차를 세어 요약 맨 위에 적고, 신규 생성 성공률·시간은 캐시 아닌 요청으로 본다.

## 실행 계획 (서버 결과 캐시를 피하는 방법)

- **캐시 키**: `odiro/agent/run.py` `cache_key("course", req.model_dump())` → 요청 필드 전부(mode·transport·region·date·start_time·end_time·day_starts·days·budget·moods·free_text·party·headcount·lodging). 스크립트가 바꾸는 값은 날짜·교통수단·시작 시각뿐이라 `프리셋:날짜:교통수단:시작시각`(결과의 `combo`)이 같으면 같은 캐시 키다.
- **캐시 위치·초기화**: 컨테이너 안 `/app/cache/tools` (diskcache·sqlite, 결과 캐시와 도구 캐시가 같은 곳). `.gcloudignore`·`.dockerignore` 가 `cache/*` 를 빼므로 배포 이미지에는 비어 있다 → **배포마다, 새 인스턴스가 뜰 때마다(min-instances 0 이라 오래 쉬면) 비워진다.** Cloud Run 의 컨테이너 디스크는 메모리 위 파일 시스템이라 캐시가 메모리 4Gi 를 나눠 쓴다.
- **날짜**: 기본 `--dates` = 측정 PC 기준 오늘 +1~+4일. `get_weather.weather()` 는 서버의 `date.today()` ~ +5일만 예보를 쓰는데, 서버(Cloud Run)는 UTC 라 KST 00~09시에는 하루 늦고, OpenWeather 5일 예보(3시간 × 40칸 = 120시간)는 +5일 낮을 일부만 덮는다. 오늘은 측정 시각이 출발 11:00 을 지났을 수 있어 뺐다. 1박 2일은 종료일(+1일)까지 +4일 안이어야 해서 시작일 +1~+3일.
- **고유 조합 수**: 날짜만으로는 당일 프리셋 4개 × 4일 + 가평 3일 = 19건 (사이트 확인에 쓴 성수 11-28 을 빼면 18건) < 필요 29건. 모자란 만큼 **사이트에서 사용자가 실제로 고를 수 있는 값 하나만** 바꾼다: ① 시작 시각 11:00 → 10:00 (Builder 의 30분 단위 시간 입력) ② 교통수단 뚜벅이 ↔ 자차. 두 값 모두 캐시 키에 들어간다. 시작 시각을 먼저 쓴다 (프리셋 성격을 덜 바꾼다).
- **모드별 고정 슬롯** (계획 29건을 한 번에 나눠 서로 겹치지 않게): idle = 수원 1건, seq = 프리셋 5개 × 4건, c3 = 성수·송도·북촌, c5 = 프리셋 5개 각 1건. `--runs 1`→idle, `--runs 20`→seq, `--concurrent 3`→c3, `--concurrent 5`→c5 로 자동으로 고른다. 그 밖의 회수는 표준 29건 뒤에서 꺼낸다(custom).
- `--date` 를 주면 예전처럼 그 날짜 하나·기본 조건으로만 요청한다 (반복하면 캐시에 걸린다).
- **이번 측정에 쓴 조합**: 프리셋 5개(성수·북촌·수원 도보, 가평·송도 자차) × 날짜 2026-11-25~11-28(예보 범위) × 시작 시각 11:00/10:00 → 29건 모두 고유. 교통수단을 바꾼 변형은 쓰지 않았다. 네 측정 모두 `--avoid gapyeong:2026-11-28,seongsu:2026-11-28`. **서버 결과 캐시(코스 단위) 적중 0회** (29건 모두 `meta.cached = false`).

## 측정 방법

요청 순서는 사이트(`frontend/src/api.ts`, `Plan.tsx`)와 같다.

1. `POST /api/course/start` — 본문은 `request.ts` 의 `defaultRequest()` 에 프리셋을 `applyPreset` 으로 덮은 값(날짜·시작 시각은 위 실행 계획). 클라이언트 상한 60초(axios 기본).
2. `GET {stream_url}` SSE — `progress` 이벤트들 → `result` 또는 `error`. 상한 150초(`STREAM_TOTAL_TIMEOUT_MS`), 스트림을 연 순간부터 잰다.
3. 사이트는 스트림이 첫 이벤트 전에 끊기면 동기 API(`POST /api/course`, 100초)로 한 번 더 요청하지만, 측정 스크립트는 자동 재시도를 하지 않고 `stream_before_first` 로 분류만 한다.

- **성공** = `result` 이벤트를 받았고 CourseResponse 모양이며 `places` 가 비어 있지 않음. 경고가 있어도 성공(경고 수는 따로).
- **실패 분류**: `sse_error`(서버 오류 이벤트) · `stream_before_first`(첫 이벤트 전 스트림 끝) · `stream_ended_no_result`(진행 중 스트림 끝) · `bad_response`(형식 오류) · `empty_course`(장소 0곳) · `http_429` · `http_5xx` · `http_other` · `network_error` · `client_timeout`(150초 초과, 시작 요청 60초 초과 포함)
- **성공률 분모** = 시도한 전체 회수. **p50·p90** = 가장 가까운 순위(nearest-rank, 정렬값의 ⌈p×n⌉ 번째). 시간은 monotonic 시계로 시작 요청부터 결과(또는 실패)까지.
- **단계별 시간**: 응답 `meta.trace`(없으면 `progress` 이벤트)의 노드별 ms. 기록이 없는 단계는 0 이 아니라 "기록 없음"으로 빼고 평균을 낸다(표에 기록 있는 표본 수).
- **웹 문서 수**(`meta.web_docs`)는 웹 검색 **결과 건수**다. 실제 외부 호출 횟수·크레딧은 응답에 없어 이 리포트에서 추정하지 않는다(Tavily 대시보드로 확인). 이번 29건은 모두 7건.
- 결과 파일에는 상태 코드·분류·시간·개수만 저장한다. 응답 본문, 오류 메시지 원문, 키·인증 헤더는 저장하지 않는다.

| parse_intent | 334 | 17 | 4 | 28 | 28 |
| retrieve | 14,064 | 8,940 | 16,456 | 27,309 | 13,061 |
| draft_course | 8,704 | 10,718 | 10,553 | 10,702 | 10,629 |
| verify_places | 120 | 564 | 2,141 | 142 | 639 |
| optimize_route | 135 | 185 | 156 | 161 | 176 |
| enrich | 5,325 | 5,878 | 6,302 | 6,716 | 6,047 |
| compose_answer | 8,335 | 9,207 | 8,071 | 9,297 | 9,075 |

- 40초 초과 성공: 13회 / 캐시 아닌 성공 29회 — 연속 20 에서는 가평 1박 2일 4건·송도 1건, 동시 3·5 에서는 전 건. 동시 측정에서 늘어난 시간은 주로 retrieve.
- 참고: LLM 호출 1회 상한 25초 + 재시도 1회(`odiro/agent/llm.py`) → 한 호출이 최악 약 50초까지 늘 수 있다.

### 해석

측정된 사실

- 동시 요청이 늘어도 **실패 없이 응답 시간만 늘었다** (평균 35.7초 → 43.8초 → 54.5초, 29건 모두 성공).
- 늘어난 시간의 대부분은 **retrieve** 에서 나왔고, 동시 수에 따라 커졌다 (8,940 → 16,456 → 27,309ms). 같은 비교에서 draft_course(10,718 → 10,553 → 10,702ms)·compose_answer(9,207 → 8,071 → 9,297ms)는 동시 수와 무관하게 거의 일정했다. enrich 는 조금 늘었다 (5,878 → 6,302 → 6,716ms).
- 최악 64.6초(동시 5, 가평 1박 2일)로 서버 timeout 120초, 사이트 스트림 제한 150초 대비 여유가 있다.
- 유휴 후 첫 요청은 retrieve 14.1초, 전체 37.5초였다. 실제 콜드스타트(새 인스턴스 기동)가 일어났는지는 확인하지 못했다.
- 동시 3 의 verify_places 평균(2,141ms)이 다른 모드(120~564ms)보다 길었다 (표본 3건).

추정 (원인은 확인되지 않음. 아래는 가능성만 나열)

- retrieve 증가의 원인은 확인되지 않았다. 가능성: CPU 1개를 여러 요청이 나눠 쓰는 자원 경쟁, 임베딩·벡터 검색 대기, retrieve 안의 외부 웹 검색 응답 지연 등.
- LLM 단계(draft_course·compose_answer)가 일정했다는 사실만으로 외부 API 전체가 병목이 아니라고 단정할 수는 없다 (retrieve 안의 외부 호출은 따로 측정하지 않았다).

## 6. Cloud Run 설정 판단

**결정: Cloud Run 설정 변경 없음.**

| 설정 | 지금 (deploy.yml) | 측정 결과 | 판단 |
|---|---|---|---|
| max-instances | 1 | 동시 5 까지 실패 0 | **유지** — 작업 상태를 컨테이너 메모리에 보관하므로 2 이상이면 `stream_url` 요청이 다른 인스턴스로 갈 수 있다 |
| concurrency | 지정 없음 (기본값) | 동시 5 를 한 인스턴스에서 처리, 실패 0 | 유지 (변경 근거 없음) |
| memory | 4Gi | 사용률 미측정 | 유지 (판단 근거가 될 측정 없음) |
| cpu | 1 | 동시 수에 따라 retrieve 증가, 실패 0 | **유지** — 시연 동시 사용 1~2명 수준에서 측정상 문제 없음 |
| timeout | 120초 | 최대 64.6초 | **유지** — 측정 최대 64.6초 |
| min-instances | 0 | 유휴 후 첫 요청 37.5초 (콜드스타트 여부 미확인) | 유지 (변경 근거 없음) |

설정을 바꾸게 되면 `.github/workflows/deploy.yml` 의 `gcloud run deploy` 줄을 고치고 다음 배포로 반영한다 (콘솔·gcloud 로 직접 바꾸면 다음 배포에서 되돌아간다).

## 7. 알려진 한계

- 표본이 작다 (유휴 후 첫 요청 1회, 동시 3·5 각 1회). 측정 모드별로 요청 조건(프리셋 구성·날짜·시작 시각)과 표본 수가 다르다.
- 측정 시점이 1회(2026-11-24 밤 시간대)다. LLM·외부 API 상태에 따라 결과가 달라질 수 있다.
- CPU·메모리 실제 사용률은 측정하지 않았다.
- 결과 캐시 적중은 0회이나, 같은 인스턴스 안의 도구 캐시(날씨·장소 조회 등)가 일부 적중했을 가능성은 있다 (프리셋 지역이 반복된다).
- 시작 시각을 10:00 으로 바꾼 변형은 기본 프리셋과 조건이 조금 다르다 (결과의 `combo` 로 구분).
- 브라우저 전체 동작(지도 렌더링 등)이 아니라 배포 API 의 SSE 생성 흐름만 측정했다. 측정 PC 의 네트워크 상태가 시간에 들어간다.
- 배포 리비전·운영 설정은 확인하지 못했다 (측정 중 배포가 없었음은 사용자가 확인).
- 웹 검색 크레딧·외부 호출 횟수는 측정하지 않는다.
- 수정(edit) 흐름은 측정하지 않는다 (코스 생성만).

### 향후 검토 후보 (효과를 보장하지 않음, 후보로만 기록)

- cpu 2 또는 검색 단계 최적화로 동시 요청 때 retrieve 지연이 줄어드는지 확인
- 작업 상태 외부 저장(Redis 등) 후 max-instances 확장
- Cloud Run timeout(120초) < 사이트 스트림 제한(150초) 불일치 정리
